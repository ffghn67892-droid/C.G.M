## 1. 제안 결론

사용자가 제안한 공통 UI·시스템 재사용과 영역별 파일 분할을 적용한다. 여기에 **게임 규칙, 상태 변경, 화면 표시의 분리**를 추가하는 것을 권장한다. 파일만 나누면 현재의 전역 변수 의존과 중복 실행이 그대로 남기 때문이다.

공통 처리와 게임별 모듈을 조합하는 작은 구조로 재편한다. 기존 JavaScript와 Electron을 유지하고, 이번 작업을 위해 UI 프레임워크나 상태 관리 라이브러리를 추가하지 않는다. 소스를 한 줄로 압축하는 작업보다 중복 구현·불필요한 계산·DOM 재생성을 줄이는 데 집중한다.

현재 UI, 게임별 보상·갱신 규칙, 기존 저장 데이터의 의미를 유지한다. 리팩터링 중 발견한 규칙 불일치는 별도 목록에 기록하며 구조 변경에 섞어 조용히 수정하지 않는다.

## 4. 공통화 설계

### 4.1 일일 퀘스트

공통 목록은 제목, 빈 슬롯, 완료 상태, 보상 선택, 버튼 배치를 담당한다. 규칙 계층은 다음 값을 제공한다.

- 최대 보유 수, 회차별 지급 수, 갱신 주기
- 완료 후 다음 갱신까지 유지할지 또는 즉시 목록에서 제거할지
- 퀘스트 종류 중복 허용 여부와 생성 방식
- 보상 선택지, 추가 XP, 연계 진행도
- 표시할 빈 슬롯 수, 직접 보상 버튼 또는 모달 선택 방식

예를 들어 KARDS는 `rewardMode: 'inline'`, MTGA는 `rewardMode: 'dialog'`로 같은 보상 선택 부품을 사용하되 현재 조작 방식을 유지한다. `rewardGold` 하나에 모든 게임을 맞추지 않고 `{gold: 50}` 또는 `{rupies: 70, redEther: 50}`처럼 재화별 보상 묶음을 전달한다.

모든 일일 기능을 하나의 거대한 함수로 합치지는 않는다. 공통 모델은 다음 세 가지로 구분한다.

1. 기간마다 추가되고 보관되는 퀘스트: 일반 누적형, 종류 중복 금지형, 스냅 시간대형.
2. 매일 고정 목록에서 일부 또는 전부를 완료하는 미션: 파크 일일, 포켓 미션.
3. 사용하면 줄고 시간으로 회복되는 자원: 듀얼리스트, 무료 팩, 겟 포인트.

유사한 표시 부품을 공유하되 각각의 갱신 계산은 해당 모델이 담당한다. 기존 KARDS 패스 추가 퀘스트와 섀도우버스 지급 개수도 조사한 현재 동작을 그대로 이관한다.

### 4.2 완료와 보상 지급

버튼은 배열 위치 대신 안정적인 퀘스트 ID를 전달한다. 모든 완료 요청은 공통 실행 경로를 통과한다.

`게임 ID·퀘스트 ID·선택 보상 → 현재 시각으로 동기화 → 대상·기간·보상 유효성 확인 → 진행도와 원장 변경 → 한 번 저장 → 필요한 화면 갱신`

보상은 게임 규칙에 등록된 선택지에서 결정한다. DOM에 들어 있는 숫자를 그대로 신뢰하지 않는다. 이미 지급한 원장 키는 다시 지급하지 않고, 모달을 연 동안 갱신 시각이 지나면 기존 선택을 거부한다. 저장 실패 시 진행도만 완료되거나 보상만 추가된 상태가 남지 않도록 변경 묶음을 취소할 수 있게 한다. 변경 대상 게임의 작업 사본 또는 변경 내역을 사용하며 매초 전체 상태를 복제하지 않는다.

초기 설정의 기수령 보상과 실제 활동은 같은 보상 계산을 사용하되 활동일 기록 여부는 명시적으로 구분한다.

### 4.3 저장 실패와 동작 순서의 구체적 처리

현재 `app.js`의 `save()`는 `localStorage.setItem`을 동기 호출한다. 단일 렌더러의 동기 이벤트 처리 중 클릭이나 타이머 콜백이 중간에 끼어드는 비동기 저장 경쟁을 현재 문제로 주장하지 않는다. 실제 위험은 **공유 메모리의 진행도·원장을 먼저 수정한 다음 저장에서 예외가 나면 화면 메모리와 저장값이 달라지는 것**이다. 용량 초과 등 쓰기 실패를 주입하여 확인해야 한다.

그 밖에 보상 모달을 열어 둔 동안의 날짜 변경, 연속 클릭이 각각 순차적으로 처리되는 경우, 포커스·절전 복귀와 타이머가 연이어 동기화하는 경우가 있다. 이들은 실행 중 동시 접근보다 오래된 선택과 중복 명령 문제로 다룬다.

새 동작 실행 경로는 다음 순서로 설계한다.

1. 명령에 게임 ID, 대상 ID, 선택 당시 회차와 안정적인 지급 키를 담는다. 확정할 때 현재 회차·잠금·완료 상태·허용 보상을 다시 검증한다.
2. 변경 대상 게임의 작업 사본에 진행도·원장·활동일 변경을 함께 적용한다. 복수 게임 초기화처럼 범위가 큰 명령만 그 범위 전체를 작업 사본으로 만든다. 기존 메모리 상태는 아직 바꾸지 않는다.
3. 작업 사본을 포함한 저장 후보를 직렬화하고 기존 저장 키에 동기 저장한다. 이 확정 구간에는 `await`, IPC 또는 모달 대기를 넣지 않는다.
4. 저장 성공 후 작업 사본을 메모리 상태에 반영하고 집계 캐시를 무효화한 뒤 화면을 갱신한다. 성공한 지급 키를 재처리해도 보상은 다시 지급하지 않는다.
5. 직렬화·저장 실패 시 작업 사본을 폐기하고 기존 메모리·합계·미완료 상태를 유지한다. 성공 알림을 표시하지 않는다. 무한 자동 재시도는 하지 않고 실패를 알린 뒤 사용자 재시도 시 현재 회차와 저장 상태를 다시 확인한다.
6. 저장 성공 후 화면 갱신이나 알림만 실패하면 이미 확정한 보상을 되돌리지 않는다. 확정 상태로 화면을 다시 표시한다. 저장 실패와 표시 실패의 예외 처리 범위를 분리한다.

검증 사례: 완료 보상 저장 실패 후 메모리·저장값 보존, 실패 후 재시도 1회 지급, 저장 성공 후 표시 실패·재실행 시 1회 지급, 동일 지급 키 연속 호출, 모달 회차 변경, 연속 복귀 동기화. 강제 종료·디스크 장애까지 데이터베이스 수준의 내구성을 보장한다고 주장하지 않는다.

현재 main 코드는 한 프로세스에서 창 하나를 만들지만 다중 앱 프로세스를 막는 단일 인스턴스 잠금은 없다. A에서 실제 실행 경로와 동일 저장소의 복수 작성 가능성을 조사한다. 복수 작성이 가능하면 C 시작 승인 범위에 단일 작성자 보장 방안을 명시한다. 단일 렌더러용 작업 사본만으로 여러 프로세스의 충돌까지 해결했다고 간주하지 않는다. 비동기 IPC 저장소로 전환하는 작업은 이번 기본 범위에서 제외하며, 필요해지면 별도 승인받는다.

### 4.4 기타 공통 기능

- 무료 보상: 회차당 지급 횟수, 잠금 조건, 수령 애니메이션, 다음 회차 재등장.
- 단계 보상: 구간 도달 판정과 중복 지급 방지. 스냅 주간과 파크 포인트가 공유하되 100포인트 상한은 파크 규칙으로 유지.
- 충전 자원: 상한, 충전 간격, 기준 시각, 소비 처리. 충전 중 추가 소비 시 기존 회복 시각을 보존.
- 패스: 무료/유료 트랙, 등급별 표, 반복 보상, 늦은 유료 활성화 시 무료 중복 지급 방지.
- 화면 부품: 퀘스트 행, 숫자 증감, 진행 바, 보상 목록, 페이지 이동, 대화상자.
- 상태 표시: 각 게임이 긴급/권장/진행 중 항목을 반환하고 공통 표시기가 우선순위를 결정. 스냅 주간·MTGA 주간 승리가 단독으로 노란 느낌표를 만들지 않는 기존 규칙 보존.
- 설정: 최초 설정·미리보기·확정의 공통 흐름과 게임별 입력 항목 분리. 미리보기 계산을 위해 전역 저장 상태를 임시 교체하지 않음.

### 4.5 사용자 편집 가능 규칙 카탈로그

게임의 기능은 이름은 달라도 갱신·조건·보상·누적·충전·수령이라는 제한된 규칙 조합으로 구성된다. 일일·주간 퀘스트만 분리하면 승리 보너스·무료 보상·충전 자원·패스가 다시 게임별 코드로 남는다. 따라서 각 게임은 `ruleCatalog`로 기능을 선언하고, 그 안의 `questCatalog`는 퀘스트 유형 규칙만 담당한다. 화면은 카탈로그와 저장된 진행 상태를 읽어 표시하고, 완료 동작은 공통 실행 경로에 게임 ID·규칙 ID·항목 ID·선택 보상 ID를 넘긴다.

사용자가 규칙을 새로 만들 때 먼저 다음 유형을 고른다. 선택한 유형에 필요한 필드만 표시하며, 다른 유형의 필드를 임의로 섞지 않는다.

| 유형 | 용도 | 핵심 선언 필드 | 예시 |
|---|---|---|---|
| `quest` | 갱신되어 등장하고 완료 보상을 받는 항목 묶음 | 갱신, 생성 수, 보관 상한, 퀘스트 목록, 허용 보상 | MTGA 일일 퀘스트, 하스스톤 주간 퀘스트 |
| `goal` | 수동으로 기록하는 특정 목표와 단계 보상 | 기간, 목표 수치, 현재 진행 입력 방식, 단계별 보상, 완료 후 처리 | MTGA 일일·주간 승리, 스냅 주간 도전, 파크 포인트 |
| `claim` | 지정 시각 또는 기간마다 직접 수령하는 보상 | 갱신, 회차당 수령 수, 잠금 조건, 보상 | 스냅 무료 크레딧·토큰, KARDS 무료 카드 |
| `resource` | 소비하면 충전되고 상한까지 회복하는 자원 | 최대치, 충전 간격, 소비 단위, 다음 회복 기준 시각 | 듀얼링크스 일반 듀얼리스트, 포켓 팩·겟 챌린지 포인트 |
| `milestone` | 동일 기간의 누적 수치에 따라 구간 보상을 지급 | 기간, 누적 원천, 구간값, 보상, 상한 | 파크 20/40/60/80/100포인트 보상 |
| `pass` | 레벨·트랙·기간에 따라 수령하는 보상표 | 기간, 레벨, 무료/유료 트랙, 보상표, 반복 규칙 | 마스터 듀얼·하스스톤·마이트앤매직 패스 |
| `counter` | 보상 없이 기록·표시만 하는 값 | 기간 또는 무기한, 단위, 입력 범위, 표시 형식 | 누적 골드, 누적 XP, 활동 일수 |

각 유형은 공통적으로 `id`, `label`, `enabled`, `source`(기본/사용자 추가), `schedule`, `rewards`, `historyPolicy`를 가진다. `schedule`은 매일 특정 시각, 매주 특정 요일·시각, 기준 시점에서 N일 간격, 기간 없음 중 하나다. `historyPolicy`는 갱신·편집·삭제 뒤 완료 항목과 보상 기록을 유지할지, 다음 경계에서 제거할지를 선언한다. 게임 고유 규칙은 우선 데이터로 표현하고, 실제 게임 규칙으로 환원할 수 없는 계산만 제한된 확장 규칙으로 둔다.

`goal`은 퀘스트와 별개로 관리한다. 사용자는 목표값과 단계 보상을 정하고, 직접 `+/-` 입력 또는 지정된 다른 규칙의 완료 횟수 연동을 선택한다. 예를 들어 MTGA 일일 승리는 일일 기간·15승 상한·승리별 보상으로, 주간 승리는 주간 기간·XP 보상으로 선언한다. 스냅 주간 도전은 일반 임무 완료 횟수를 원천으로 참조하되, 사용자에게 즉시 할 일이 있다는 노란 상태 표시는 만들지 않는 표시 정책을 별도로 둔다.

퀘스트 카탈로그의 최소 형식은 다음과 같다.

퀘스트 카탈로그의 최소 형식은 다음과 같다.

```js
{
  id: 'daily',
  label: '일일 퀘스트',
  reset: { kind: 'daily', time: '18:00', timezone: 'Asia/Seoul' },
  // 또는 { kind: 'weekly', weekday: 0, time: '18:00', timezone: 'Asia/Seoul' }
  // 또는 { kind: 'intervalDays', days: 3, anchor: '2026-01-01T00:00:00+09:00' }
  spawnCount: 1,
  capacity: 3,
  rewardTypes: [
    { id: 'gold-500', label: '500 골드', rewards: { gold: 500 } },
    { id: 'gold-750', label: '750 골드', rewards: { gold: 750 } }
  ],
  quests: [
    { id: 'win', label: '승리하기', rewardTypeIds: ['gold-500', 'gold-750'] }
  ]
}
```

`reset.kind`는 매일 특정 시각, 매주 특정 요일·시각, 기준 시점에서 N일 간격을 표현한다. `spawnCount`는 갱신마다 추가되는 수이고, `capacity`는 누적 보관 상한이다. 보상은 먼저 `rewardTypes`에서 재화 묶음으로 정의한 뒤 각 퀘스트가 허용한 `rewardTypeIds`만 선택한다. 따라서 MTGA의 500/750 골드와 섀도우버스의 복수 재화 선택도 같은 형식으로 표현할 수 있다.

게임 최초 설정에는 기본 `ruleCatalog` 확인 단계를 넣는다. 사용자는 제공된 규칙을 그대로 확정하거나, 유형 선택 → 이름 → 유형별 일정·목표·상한·보상 → 다른 규칙과의 연동 → 표시 정책 순서로 수정·추가한다. 이후 설정에서 바꾸는 흐름도 같은 편집기를 사용한다. 입력값은 저장 전 ID 중복·음수·상한 미만·알 수 없는 보상 또는 원천 규칙 참조·유효하지 않은 KST 시각·순환 연동을 검증한다.

기본 제공 규칙과 사용자 추가 규칙은 출처를 구분해 저장한다. 최초 설정을 확정하기 전에는 미리보기 상태만 바꾸며, 확정 뒤 편집·삭제해도 이미 완료한 퀘스트, 과거 보상 원장, 현재 진행 기록을 고아 상태로 만들지 않도록 ID와 당시 보상 정의를 보존한다.

이 카탈로그는 C의 저장 확정 계층 위에 D와 E 단계에서 순차적으로 올린다. C에서 게임 규칙을 이 형식으로 일괄 이관하거나 사용자 편집 화면을 만들지는 않는다. D에서는 KARDS의 `quest`와 `claim`을 첫 적용 대상으로 삼고, E1의 MTGA에서 `goal`을 적용한다. 이후 각 게임 이관 승인 단계에서 해당 게임의 예외 규칙이 이 형식으로 충분한지 검증하고 필요한 공통 필드만 추가한다.

작은 게임은 불필요하게 파일 세 개를 만들지 않고 하나로 시작한다. 여러 게임에서 실제로 재사용되는 개념만 공통 영역으로 올린다. 한 줄 함수마다 파일을 만드는 식의 과도한 분할은 하지 않는다.

최종적으로 명시적인 `import/export`를 사용하는 ES 모듈 구조를 권장한다. 현행 패키지 목록을 바꾸지 않는 동안에는 `manager.js`가 렌더러의 단일 초기화 진입점이다. 별도 `renderer-entry.js`로 옮기는 일은 패키지 파일 목록 변경을 수반하므로, 사용자가 설치 관련 설정 작업을 다시 승인한 뒤에만 진행한다. 기존 `index.html` 직접 열기의 지원 여부도 이 단계에서 확인하고, 제약이 있으면 숨기지 않고 실행 경로를 명시한다.

의존 방향은 `화면 → 동작 실행 → 게임 규칙·공통 기능 → 저장/시간/원장`으로 제한한다. 공통 규칙은 DOM을 참조하지 않고, 렌더러는 보상 지급이나 저장을 실행하지 않는다. 테스트에서 시각·ID 생성을 주입할 수 있게 한다.

### 5.1 Electron 프로세스 경계

위 `src/` 구조는 **렌더러의 게임 관리 코드**에 적용한다. B단계에서는 설치 관련 파일을 바꾸지 않고 기존 `manager.js`를 렌더러의 단일 초기화 경계로 확정했다. 별도 `renderer-entry.js`로의 이름·파일 이동은 패키지 파일 목록 변경을 승인받은 후에만 검토한다.

| 영역 | 현재 진입점·책임 | 리팩터링 경계 |
|---|---|---|
| main 프로세스 | `electron-main.js` → `desktop-main.js`; 창·트레이·외부 상점·시스템 알림·절전 복귀 | 기본 위치와 CommonJS 실행 방식 유지. 렌더러의 규칙·DOM 모듈을 가져오지 않음 |
| preload | `preload.js`; `contextBridge`로 `window.deckroom` 노출 | `openShop`, `setTray`, `alarm`, `onResume`의 제한된 기능 유지. 임의 IPC나 Node API를 노출하지 않음 |
| renderer | `index.html`과 현재 게임 스크립트, DOM, localStorage | 공통 기능·게임별 모듈로 이관. Node `require`나 파일 시스템 API에 의존하지 않음 |

현재 창은 `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`다. ES 모듈 전환을 위해 이 설정을 완화하지 않는다. `package.json` 전체에 `type: module`을 적용해 main/preload의 기존 CommonJS를 함께 바꾸는 방식도 피한다. main의 IPC 발신자·메인 프레임 확인과 외부 URL 제한을 보존한다.

초기화는 한 번만 실행하며, 재초기화가 필요한 경우 타이머와 이벤트 구독의 해제 경로를 둔다. 현재 `onResume`은 해제 함수를 반환하지 않으므로 브리지까지 변경할 필요가 있는지는 B에서 결정한다. 변경 시 해당 단계 범위 안에서 호환 API와 구독 중복 방지를 검증한다.

B에서는 실제 개발용 `loadFile` 경로, ES 모듈 경로, preload 노출, 렌더러의 Node 접근 차단, 복귀 구독 중복 여부를 확인한다. DOM 모의 테스트만으로 이 경계를 통과했다고 보고하지 않는다. main/preload 변경 시에만 해당 소스 실행 검증을 확대하며, 설치본 실행·패키징 검증은 제외한다.

## 6. 성능 개선 우선순위

| 우선순위 | 변경 | 기대 효과와 주의점 |
|---|---|---|
| 1 | 매초 전체 `JSON.stringify(state.games)` 비교 제거 | 기록이 늘수록 증가하는 불필요한 순회·문자열 할당 제거 |
| 1 | 렌더링에서 동기화·보상·저장 제거 | 화면을 다시 그릴 때 발생하는 중복 처리와 저장 감소 |

| 2 | 원장 합계와 출처별 합계 캐시 | 스냅 요약·메인 목록 등의 반복 전체 집계 감소 |

| 3 | 다음 갱신·충전·알람 시각을 기준으로 스케줄링 | 변화 없는 시간의 불필요한 게임 동기화 감소 |

스케줄러 개선은 두 단계로 한다. 먼저 현재 1초 동작을 유지하면서 변경 감지 비용을 없애고, 이후 가장 가까운 갱신·충전·패스 종료·음소거 해제·이벤트 종료 시각을 예약한다. 초 단위 숫자는 필요한 화면에서만 갱신한다. 포커스 복귀·절전 복귀·시계 변경에 대비해 절대 시각으로 재계산하고, 경량 보정 확인을 둔다. 미확인 알람의 30초 반복도 유지한다.

원장은 보상의 기준 기록으로 유지한다. 합계 캐시는 최초 로드·이관·초기화·설정 확정에 맞춰 생성하거나 무효화하며, 원장 수정 이후 오래된 값이 남지 않게 한다. 용량 감소를 위해 지급 기록을 지우거나 임의 합산해 중복 방지 키를 잃는 방식은 사용하지 않는다.

메모리 집계 캐시와 파일 분할로 소스·메모리 일부가 증가할 수 있다. 소스 바이트 감소, 저장 데이터 크기, 실행 시간은 별도 지표이며 동일한 개선으로 주장하지 않는다. 출시 파일 최소화나 설치 파일 크기 최적화는 현재 사용자 지시상 제외한다.

## 7. 제거·유지 기준

삭제 후보는 기존 스냅·마이트앤매직 렌더러처럼 교체된 구현, 도달하지 않는 구형 화면과 모달, 숨겨진 수동 갱신 요소, 사용하지 않는 인자·선택자·스타일, 중복 보상 집계, 부정확한 주석이다.

삭제 전에 다음을 확인한다: 전체 참조 검색, 실제 초기화·이벤트 연결 경로, 테스트 사용처, 저장 데이터 이관에서의 사용 여부. 전역 함수가 나중에 덮어써진다는 이유만으로 원본 파일의 초기화 부작용까지 미사용으로 취급하지 않는다. 동적 CSS 클래스도 문자열 검색 결과만으로 삭제하지 않는다.

구버전 저장값, 원장 중복 방지 키, 완료 퀘스트 유지 규칙, 보상표의 희귀도 구분, 확인되지 않은 보상의 미입력 상태, 삭제한 이벤트의 재생성 방지 표식은 보존한다. 구형 런타임 코드는 제거하더라도 저장 이관 코드는 별도로 유지할 수 있다.

- `scripts/desktop-smoke.cjs`는 소스 실행 시 브리지 존재, Node 접근 차단, 재로드 저장 보존, 트레이 닫기를 확인하는 경로가 있다. 모든 IPC 오류·보안 분기·실제 OS 절전은 검사하지 않는다. 과거 통과 기록과 이번 단계의 새 실행 결과는 구분한다.
- 저장 실패 후 복구·재시도, 저장 성공 후 표시 실패, 모든 모달의 키보드 초점 복귀, 전체 구버전 저장 형식 조합은 현재 충분히 검증됐다고 말할 근거가 없다.

A에서 수행할 커버리지 점검:

1. 요구사항별 정상·경계·실패·복원 사례와 테스트 위치를 연결하고, 검증됨/부분/공백으로 구분한다. 보상·저장·갱신의 공백에 우선순위를 둔다.
2. 설치된 Node에서 지원되는 범위로 코드 커버리지를 수집한다. 현재 하네스가 스크립트를 VM에 합쳐 실행하므로 소스 파일별 매핑의 신뢰성을 확인한다. 매핑되지 않는 코드는 미측정으로 표시하며 하네스 커버리지를 앱 커버리지로 보고하지 않는다. 필요하면 계측용 하네스에 파일 식별자를 붙인다.
3. 런타임 코드·테스트 하네스·생성 데이터의 분모를 구분한다. 측정되지 않는 Electron main/preload는 별도 미측정 항목으로 보고한다. 보상표 58.3 KB가 전체 커버리지 비율을 왜곡하지 않도록 데이터는 별도 집계한다.
4. 실패 주입·복귀 순서·읽기 전용 렌더링 등 새 설계의 계약을 검증할 보강 목록을 만든다. 현재 결함을 보여 주는 사례는 알려진 실패로 기록하고 이관 전 해당 단계의 종료 조건에 반영한다. 실패를 무조건 허용하는 새 기준선으로 고정하지 않는다.
5. A 결과물은 `REFACTOR_BASELINE.md`와 실행·계측 결과다. 중요 공백에 대한 확인 없이 B 이후 작업을 시작하지 않는다. 커버리지 퍼센트 하나를 임의 합격선으로 삼지 않는다.

### 8.3 게임별 착수 순서의 근거

KARDS는 가장 단순한 게임이라기보다 **첫 공통화에서 검증할 기능을 적당한 범위로 포함한 게임**이다. 일일 퀘스트는 최대 3개, 완료 시 두 종류의 단일 골드 보상이며 승리 횟수와 주간 진행의 연쇄 계산이 없다. 무료 카드·빈 슬롯·수량 보정·접힌 목록까지 공통 UI를 시험할 수 있고 최근 관련 테스트와 화면 확인이 있다. 다만 패스 추가 지급·완료 유지·주간 상자는 예외로 남아 있으므로 위험이 없다고 보지 않는다.

다음 MTGA에서 모달과 XP·승리 연계를 검증하고, 하스스톤에서 동일 큐와 직접 수행 주간 목록의 재사용을 확인한다. 마이트앤매직은 복수 주기·패스, 섀도우버스는 복수 재화·파크 상한, 마스터 듀얼은 종류 중복 금지·9개 큐, 스냅은 별도 시간대 발급 정책으로 점차 확장한다. 듀얼링크스로 충전 자원 한 종류를 먼저 이관한 뒤 포켓에서 두 종류 충전과 3개 달성 조건을 조합한다. A에서 확인한 공백이 크면 다음 단계 승인 요청에 순서 조정 이유를 제시한다.

### 8.4 실패한 이관의 복구

프로젝트 루트에 현재 `.git`이 없음을 확인했다. 커밋으로 되돌릴 수 있다고 가정하지 않는다. A 승인 후 `.refactor-checkpoints/`에 최초 기준점을 만들고 이후 승인받은 단계 시작마다 코드·설정·테스트·관련 문서의 파일 목록, 상대 경로, SHA-256, 내용을 보관한다. `node_modules`, `dist`, 실제 사용자 프로필은 복사 대상에서 제외한다. 단계 중 추가한 파일도 별도 목록에 기록한다. Git을 도입하더라도 사용자 작업을 포함한 일괄 강제 초기화는 하지 않는다.

각 단계 종료 시 변경 목록, 검증 결과, 남은 문제, 기준점 위치를 기록한다. 합계·갱신 규칙 불일치, 모듈 로딩 실패, 저장 실패 복구 불능이 있으면 다음 단계로 진행하지 않고 현재 승인 범위에서 원인을 수정한다. 완료 가능성이 불명확하거나 범위가 커지면 실패 지점을 보고하고 재계획한다.

복구가 필요한 경우 실행 중인 QA를 중단하고 실패 버전도 보관한다. 기준점과 변경 목록을 비교하여 해당 단계가 수정한 파일만 복원하고, 해당 단계가 새로 만든 파일만 제거한다. 대상 경로가 작업공간 내부인지 확인한다. 기록된 수정 이후 사용자나 다른 작업이 같은 파일을 바꿨으면 자동 덮어쓰지 않고 충돌 내용을 보고한다. 단계별 복구 지점이 확보된 상태에서 승인 범위 안의 변경만 되돌린다.

게임 저장값의 복구와 코드 복구는 구분한다. 이관 검증은 합성 데이터와 전용 QA 프로필을 사용하고 실제 사용자 프로필을 읽어 덮어쓰거나 초기화하지 않는다. QA 상태는 테스트 사본에서 복원한다. 코드 복구를 이유로 사용자의 새 활동 기록을 과거 값으로 되돌리지 않는다. 실제 데이터 이관이 필요해지는 경우 별도 승인과 버전별 복구 계획을 먼저 받는다.

### 8.5 예상 공수와 일정

아래는 기존 구조를 점진적으로 전환하고 필요한 검증을 수행하는 **개발자 1인 기준의 초기 계획 공수**다. 도구 실행 시간이나 AI의 실제 완료 시간을 보장하는 수치가 아니다. 사용자 승인 대기·추가 기능·설치 작업은 제외한다. A의 테스트 공백·계측 결과를 바탕으로 이후 범위를 재산정한다.

| 승인 단위 | 예상 작업 시간 |
|---|---:|
| A: 기준선·커버리지 공백·복구 기준점 | 3~5시간 |
| B: 모듈 연결·중복 정의·하네스 | 5~8시간 |
| C: 저장·보상·시간·명령 확정 | 8~12시간 |
| D: KARDS | 4~6시간 |
| E1: MTGA | 3~5시간 |
| E2: 하스스톤 | 2~4시간 |
| E3: 마이트앤매직 | 4~7시간 |
| E4: 섀도우버스 | 4~7시간 |
| E5: 마스터 듀얼 | 5~8시간 |
| E6: 마블 스냅 | 4~7시간 |
| E7: 듀얼링크스 | 3~5시간 |
| E8: TCG 포켓 | 4~6시간 |
| F: 성능 개선·전후 측정 | 6~10시간 |
| G: 미사용 코드·CSS 정리·문서화 | 3~5시간 |
| 합계 | 58~95시간 |

불확실성 여유 20~30%를 포함하면 약 70~124시간, 하루 8시간 기준 약 9~16작업일 규모다. 각 단계 승인 전 범위가 달라졌다면 추정을 갱신한다. 특히 VM 커버리지 매핑, 모듈 로딩과 복수 작성자 문제, 구버전 저장 공백이 주요 변동 요인이다.

승인 흐름은 `단계 계획 제시 → 사용자 허락 → 기준점 확보 → 작업·해당 검증 → 완료 또는 실패 보고 → 다음 단계 허락 요청`이다. 실패한 단계를 완료로 표시하지 않고, 다음 단계 승인을 미리 묶어서 받은 것으로 해석하지 않는다.

## 9. 측정 기준과 최종 인수 조건

성능은 동일한 개발 환경·동일한 합성 데이터·동일한 조작으로 전후 비교한다. 워밍업 후 여러 번 측정하여 중앙값과 범위를 기록한다. 처음에는 계측에 필요한 최소 사례만 사용하고 병목이 확인된 경우 확장한다.

- 보상 기록이 적은 상태와 많은 상태에서 대기 중 동기화 시간·전체 직렬화 횟수.
- 퀘스트 한 건 완료, 메인 탭 열기, 게임 전환의 처리 시간과 저장 횟수.
- 한 번의 동작에서 화면 패널을 다시 만드는 횟수와 원장 전체 집계 횟수.
- 실행 코드·CSS의 원본 바이트 변화. 생성된 보상표 데이터는 별도 집계.

최종 조건:

1. 퀘스트 완료·갱신·보상·알림·초기화가 현재 승인된 동작과 일치한다.
2. 기존 저장 기록의 보상 합계·진행도·패스·등록일·활동일이 보존된다.
3. 활성 탭을 바꾸지 않고 모든 게임을 동기화할 수 있다.
4. 함수 덮어쓰기로 기능을 연결하는 구조와 매초 전체 상태 문자열 비교가 없다.
5. 읽기 전용 화면 갱신은 저장·보상을 발생시키지 않는다. 상태 변경은 하나의 확정 경로에서 저장한다.
6. 완료된 공통 컴포넌트는 여러 게임이 실제로 사용하며, 사용하지 않는 추상 계층을 남기지 않는다.
7. 실제 실행 측정과 삭제 내역으로 개선을 보고한다. 확인하지 않은 감축률·속도 향상을 약속하지 않는다.

A·B·C·D는 완료했으며 다음 승인 요청 범위는 E1뿐이다. E1~E8, F, G 각각을 시작하기 전에 사용자 허락을 받는다. KARDS에서 공통 처리 방식과 데이터 보존을 검증한 뒤 나머지 게임에 순서대로 적용한다. 최종 범위는 전체 게임이며, 첫 적용 단계가 끝났다고 전체 리팩터링이 완료된 것으로 처리하지 않는다.
